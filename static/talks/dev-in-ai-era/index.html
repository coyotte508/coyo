Le point de départ

Comment on travaillait avant

La compétence prenait des années

La maîtrise d'un stack venait du temps passé sur la doc, le code source et les bugs. Chaque nouvelle technologie : des mois de montée en charge.

Les tâches transverses = corvée

Traduire une app en plusieurs langues, adapter une UI à une charte : des semaines de travail mécanique à faible valeur ajoutée.

Les gros refactors = risque

Déplacer de gros pans de code : lent, risqué, et dépendant d'une seule personne capable d'en garder la vision complète.

Les outils internes = jamais prioritaires

Outils internes, scripts, prototypes : systématiquement perdants face au produit principal dans la file des priorités.

Ce qui a débloqué

Les capacités qui ont tout changé

👀 Vision

Capture d'écran → correction. Maquette → application. L'UI, longtemps « difficile à spécifier », devient directement adressable.

🔧 Usage d'outils

L'agent exécute des commandes, lit et écrit des fichiers, teste son travail, s'auto-corrige. De la suggestion à l'action.

🧩 Bases qui se combinent

Long contexte, sorties structurées, sous-agents, skills. De petites capacités qui s'additionnent.

🏋️ Exercice recommandé : construire son propre harnais

Une couche fine qui appelle le modèle — sa propre boucle d'outils, son propre mini agent. On comprend les capacités et limites réelles bien mieux qu'avec un produit packagé.

Open source vs modèles fermés

📉 L'écart s'est effondré

Il y a 2 ans, « open » voulait dire « deuxième classe ». Aujourd'hui, les modèles open-weights (DeepSeek, Qwen, GLM, Kimi…) sont à quelques points de la frontière — parfois devant.

Stanford AI Index 2026 : ~3,4 % d'écart open/fermé (mars 2026)

🔓 Ce que l'open change

Souveraineté des données · coût 10-15× moindre · pérennité (les poids restent) · pédagogie : on peut regarder dedans, fine-tuner, auditer.

🔒 Ce que le fermé garde

Avance sur le raisonnement multi-étapes le plus dur, outillage intégré, sécurité clé en main.

🧩 En pratique : on mélange

Stacks de production typiques : open pour le volume, frontière fermée réservée aux cas difficiles.

Perfs & souveraineté

Déployer ses propres modèles

📈 La courbe des perfs

SWE-bench Verified (« résoudre une vraie issue GitHub ») : ~49 % (oct. 2024) → ~77 % (sept. 2025) → 95 %+ (été 2026). Et le coût s'effondre en même temps.

🖥️ Self-hosting : la barre a baissé

Ce qui demandait un labo il y a 2 ans tient sur quelques GPU — vLLM, SGLang, TGI. Un modèle open-weights récent rivalise avec les frontières fermées d'hier.

🏢 Ce que ça change en entreprise

Inférence interne pour les données sensibles, coûts prévisibles, pas de dépendance totale à un fournisseur, latence maîtrisée.

⚖️ Honnêteté

Ça reste un investissement : compétence MLOps, infra GPU, observabilité. Mais la barre à l'entrée a baissé d'un ordre de grandeur.

Où ça brille

Ce qu'une IA bien promptée fait très bien

  • Combler les trous de connaissance — nouveaux langages, stacks inconnus, codebases étrangères
  • Traduire et adapter — i18n, portage, chartes graphiques spécifiques
  • Refactorer de gros pans de code — un contexte qu'aucun humain ne peut tenir

  • Refactor, benchmark, debug, tests — générer des tests, diagnostiquer, mesurer
Bien promptée, l'IA transforme des semaines de corvée en heures de relecture.

Exemple concret, en production

🌙 moon-bot — un agent au quotidien

Slack → agent de coding

Un bot qui reçoit des commandes dans Slack, les transmet à un agent de coding via SDK, dans un pod privilégié avec skills et outils. Il aide à supporter le hub Hugging Face tous les jours.

~300 commits · ~50 000 lignes · 100 % agentique

Revue de code assistée par IA

On le mentionne dans GitHub : il modifie la PR en cours, en crée une autre, ou ouvre une issue.

Et selon la PR, une review faite par soi-même suffit : on ouvre, on relit, on approuve — un vrai gain de temps sur les changements à faible risque.

Mémoire & outils

Mémoire persistante sur buckets HF, accès outillé à l'infra interne, sandbox réseau. Un agent 'employé', pas un chatbot.

Où la friction reste

Le cœur de métier reste exigeant

🔍 Revues de code humaines

Sur les projets en production, la review reste la norme — et son importance augmente avec le volume de code généré. On review l'IA comme un junior très rapide et très confiant.

🔐 Sécurité

Un agent avec accès aux outils internes = une surface d'attaque. Sandboxing, permissions minimales, secrets hors du contexte, audit des actions.

🏗️ CI/CD & infra as code

Tests, pipelines, infra déclarative : la discipline n'a pas changé. Plus le code arrive vite, plus les garde-fous automatisés sont indispensables.

🧭 Propriété & cohérence

L'IA génère du code à l'infini. Elle ne génère pas « une codebase qu'on aime encore dans 6 mois » — ça, c'est le rôle de l'équipe.

Infra as code : se bootstraper, pas stagner

☸️ Kubernetes, Terraform, Helm

Syntaxe verbeuse, connaissance de surface : personne ne la retient. L'IA connaît toutes les APIs et les bonnes pratiques par défaut.

🚀 Jours de doc → minutes

Se bootstraper presque instantanément — et se concentrer sur ce qu'on veut vraiment faire : l'architecture, le métier.

🌙 Exemple vécu : moon-bot

Pod k8s, chart, réseau, provisionnement : couche infra écrite par l'agent, relue par moi. Sans ça, le projet ne serait jamais né.

Déléguer le mécanique, garder le conceptuel — c'est exactement ça, le jugement.

Arbitrage d'architecture

Plutôt que grossir le monorepo : l'offshoot

✂️ Réécrire un bout from scratch

Extraire une partie du monorepo en service à part : les IA sont très fortes pour ça.

🔗 L'infra as code fait la glue

Nouveau service, nouveau chart, nouveau pipeline : le câblage qui coûtait cher devient rapide.

🏃 Moins de frictions ensuite

L'offshoot se modifie avec moins de protocoles que le projet principal : cycle propre, itération rapide. Réintégration possible plus tard.

Exemple vécu : moon-bot et moon-ide — nés à côté, itérés vite.

En collaboration

Ne pas slopper les autres

🗑️ Le slop

Déverser la sortie brute de l'IA sur quelqu'un d'autre — copier-coller un pavé générique dans une PR, un commentaire, un ticket.

Si tu ne fais que relayer ce que dit l'IA, tu es juste un intermédiaire inutile : l'autre pourrait l'interroger directement.

✍️ Écris tes propres mots

Descriptions de PR et commentaires de review : écrits par toi. L'IA peut produire le code ; le sens, le contexte, le pourquoi — c'est toi.

Ta valeur est dans ce que tu ajoutes à la sortie brute. Trois phrases précises valent mieux qu'un pavé générique.

Le piège

Vos questions biaisent les réponses

❓ Le cadre que vous donnez

Demandez « comment faire X avec Y » — l'IA ne dira jamais « vous ne devriez pas faire X ». Prenez du recul régulièrement : autre solution ? pivot ?

⚖️ Jugement > intelligence

Même les modèles les plus puissants (les fables du moment) n'ont pas toujours le meilleur jugement.

Quelqu'un doit pouvoir expliquer « pourquoi cette architecture ? » sans répondre « parce que l'IA l'a fait ».

Le vrai défi

Continuer à apprendre — délibérément

🎓 Avant : l'autodidactie marchait

Se confronter aux problèmes était le programme. On pouvait être autodidacte — la friction elle-même enseignait.

⚠️ Maintenant : la friction a disparu

L'IA supprime exactement l'effort qui formait. Sans rigueur, on livre pendant des années sans construire les modèles mentaux en dessous.

✅ Tout n'est pas perdu

Les compétences info se transposent bien : les gens en info ont un avantage net pour vibe-coder / diriger l'IA — on sait ce qu'on demande, lire le résultat, et détecter quand c'est faux.

📚 L'enseignement supérieur reprend de la valeur

Concepts, algorithmes, fondamentaux — appris sans tout donner à l'IA. L'apprentissage structuré impose une profondeur que le prompting seul n'impose pas.

Traiter l'IA comme un tuteur, pas un oracle.

📖 Étude (Anthropic, 2026)

Essai contrôlé randomisé : assistance IA → −17 % de maîtrise au quiz (surtout le debug). Mais ceux qui l'utilisaient pour comprendre (explications, questions conceptuelles) gardaient le niveau des codeurs à la main.
